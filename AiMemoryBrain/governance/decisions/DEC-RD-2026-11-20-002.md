## 1. Context

The governance structural checks were introduced through an independent CI change.

The implementation provides an automated structural validation program and a GitHub Actions workflow. However, the existence of a failing check does not itself establish a repository-level merge prohibition.

Independent review REV-2026-11-20-004 identified that PR #5 had a failing check while remaining mergeable. The repository had no required status check rule.

The repository uses an active ruleset (ID `27711552`). Its original configuration included pull request requirements, deletion protection, and non-fast-forward protection, but did not include `required_status_checks`.

The ruleset reports:

- `enforcement: active`
- `bypass_actors: []`
- `current_user_can_bypass: never`

The classic branch protection endpoint is not configured; protection is managed through rulesets.

### 1.1 Decision Level Classification

The original L2 classification is superseded by this L3 classification.

N-06 Section 2.4 explicitly classifies changes that alter security boundaries or permission models as L3.

This change modifies the repository's ruleset and changes the conditions under which pull requests are authorized to merge. It therefore changes the repository's effective merge authorization boundary and permission model.

The applicable classification rule is:

**When one change satisfies multiple decision-level criteria, the highest applicable level governs.**

Consequently, L3 applies even if other aspects of the implementation independently satisfy L2 criteria.

This is a governance classification correction, not a change to the original enforcement implementation.

## 2. Decision

### 2.1 Independent CI Implementation

The governance structural checks remain an independent CI change rather than being inserted into PR #2.

Reasons:

- PR #2 establishes the original governance requirement. Mixing CI infrastructure implementation into that PR would combine the requirement's introduction with its enforcement implementation.
- An independent PR provides a separately reviewable implementation boundary, allowing the workflow, validation behavior, and enforcement configuration to be evaluated independently.
- The separation preserves traceability between the original governance requirement and the subsequent machine-enforcement mechanism.

Pure documentation changes are not categorically exempted from structural governance checks.

Documentation changes can alter governance requirements, directory contracts, references, and repository structure. Exempting all documentation changes would leave a meaningful part of the governance surface outside automated validation.

### 2.3 Required Status Check

Add a `required_status_checks` rule for the actual Governance structural checks job context.

The configured check is:

- Context: `Governance structural checks`
- GitHub Actions integration ID: `15368`
- Integration slug: `github-actions`

The integration ID was obtained from the actual check-producing application (`app.id=15368`, `app.slug=github-actions`).

The required check must be associated with the expected GitHub Actions integration, not merely matched by its display name. Binding the check to the integration ID prevents another GitHub App from satisfying the requirement by submitting a check with the same context name.

### 2.4 Bootstrap Handling

PR #4 introduces the workflow and is therefore a bootstrap change.

The original assumption that required-check configuration must wait until after PR #4 merges has been disproved by operational execution.

The workflow is available for check execution, and the required-check rule was configured before PR #4's final merge decision.

The actual execution sequence was:

1. Configure the required status check in existing ruleset `27711552`.
2. Perform positive validation using a passing check.
3. Perform negative validation using a failing check.
4. Read the ruleset back through the API and verify its effective configuration.
5. Independently review the configuration and enforcement evidence.
6. Make the merge decision for PR #4, subject to its new head receiving a successful required check.

The workflow trigger types are:

`opened`, `synchronize`, `reopened`, and `ready_for_review`.

A new commit pushed to PR #4 produces a `synchronize` event and triggers another check run. The previous head's successful result cannot substitute for the new head's required successful result.

This ordering does not claim that PR #4 has already been merged or that its final head has already passed the required check.

The original bootstrap assumption is retained here as a historical decision record. It is not an outstanding implementation requirement.

### 2.5 Unrelated Build Dependencies

Do not introduce `cargo test` as part of this governance CI change.

The checks enforce repository governance and structural contracts. Cargo test is not an appropriate substitute for those checks, and no demonstrated requirement establishes that compiling or testing Rust code is necessary for this change.

Adding cargo execution would introduce unrelated build dependencies and execution requirements without strengthening the specific governance contract being enforced.

## 3. L3 Side-Effect Assessment

### 3.1 Dependency Dimension

The implementation introduces or relies on the following execution dependencies.

**GitHub Actions — `actions/checkout`**

This action provides repository checkout functionality to the workflow.

Its version must be pinned to an immutable full commit SHA rather than a mutable branch or floating major-version reference.

A version tag alone is not an immutable supply-chain guarantee. A compromised upstream release or changed tag could affect future workflow executions.

The repository must retain the action's version and SHA reference in the workflow so that changes can be independently reviewed.

**GitHub Actions — `actions/setup-python`**

This action selects and configures the Python runtime.

It must likewise be pinned to a full commit SHA.

The Python interpreter version must be explicitly selected rather than relying on an unspecified runner default. Runtime upgrades must be reviewed and tested as dependency changes.

The action itself and the selected Python distribution are separate supply-chain inputs.

**Python standard library and Git subprocess**

The validation program uses Python standard-library facilities and invokes Git through a subprocess.

No additional third-party Python package is required for these operations.

The Python standard library is coupled to the selected interpreter version. Changes in interpreter behavior can affect filesystem handling, subprocess behavior, encoding, and exception handling.

The Git executable is supplied by the runner environment. Its version is not independently fixed merely by pinning the Python interpreter.

Git command availability, supported options, repository metadata, and checkout depth must therefore be treated as runtime assumptions.

**Supply-chain residual risk**

Pinning GitHub Actions to immutable SHAs reduces mutable-reference risk but does not establish that upstream source code is uncompromised.

The required status check also does not independently prove workflow integrity or the integrity of every dependency used by the workflow.

These remain residual risks requiring separate supply-chain governance.

### 3.2 Maintenance Dimension

The governance validation program is maintained by the repository owner acting as the project's technical maintainer.

The maintenance responsibility includes:

- Maintaining the structural validation script.
- Maintaining the GitHub Actions workflow.
- Maintaining the mapping between validation rules and governance requirements.
- Updating tests when governance contracts change.
- Reviewing changes to the required status check context.
- Maintaining compatibility with the supported Python and Git runtime.

The script is coupled to N-01 and N-06 in several areas:

1. Repository directory and document structure are derived from the structural contracts defined by the governance documentation.
2. Validation behavior must remain consistent with the applicable governance requirements.
3. Severity and classification expectations must not be silently weakened by implementation changes.
4. References and required governance artifacts must remain synchronized between documentation and automated validation.

When N-01 or N-06 changes, the maintainer must determine whether the script and its tests also require modification.

If a governance rule changes but the script is not updated, two failure modes are possible:

- **False acceptance:** The script continues accepting a structure that no longer satisfies the revised governance requirement.
- **False rejection:** The script continues enforcing an obsolete requirement and rejects a structure that is valid under the revised governance contract.

A successful CI run cannot establish that the underlying governance documentation and executable rules remain semantically synchronized.

Governance documentation changes therefore continue to require human review.

### 3.3 Licensing Dimension

The repository declares `Apache-2.0` as its license.

The new validation script and workflow are intended to be distributed under the repository's declared Apache-2.0 licensing framework, subject to confirmation of the actual copyright and licensing metadata.

The repository's copyright ownership issue remains unresolved.

PR #1 ITEM-03 remains `FAIL`. The legal identity of the copyright holder has not been established.

Accordingly:

- This decision does not convert the repository's license declaration into proof of ownership.
- This decision does not establish that every newly introduced file has complete copyright attribution.
- The licensing assessment is conditional on the repository's existing Apache-2.0 declaration and remains subject to resolution of ITEM-03.

No claim of completed copyright verification is made.

### 3.4 Operations Dimension

The workflow executes as a GitHub Actions check.

A failing required check prevents the pull request from being merged through the demonstrated repository merge path.

However, the repository currently has no configured notification mechanism for governance CI failures.

There is no established notification guarantee to the repository owner through email, chat, or another independent alerting channel.

The absence of notification configuration is a residual operational gap.

Potential environmental failure conditions include:

- An unexpected Python interpreter version.
- An incompatible or unexpectedly upgraded Git version.
- Missing Git executable or runtime dependencies.
- Shallow checkout behavior that prevents a validation command from accessing required repository history.
- Missing files or metadata caused by checkout configuration.
- Runner environment changes.
- GitHub Actions infrastructure failures.

A failed workflow must not automatically be interpreted as proof of a governance violation.

The diagnostic distinction is:

**Actual governance violation**

The workflow executed successfully, the required repository inputs were available, and the validator reported a specific structural or governance contract violation.

**Environment or infrastructure failure**

The workflow could not reliably execute its validation because a required runtime, executable, repository object, file, or platform service was unavailable or incompatible.

When a failure occurs, the maintainer must inspect:

1. The complete workflow logs.
2. The Python and Git versions.
3. The checkout configuration and available repository history.
4. The validator's exit status and diagnostic output.
5. Whether the failure reproduces under a known-good local or CI environment.

An environmental failure must not be recorded as a confirmed governance violation without supporting evidence.

Conversely, an environmental failure does not satisfy the required successful-check condition.

Until a successful run exists, the required status check remains unsatisfied.

**Residual operational gap:** No automated notification mechanism is currently configured. Detection therefore depends on GitHub check visibility and the responsible maintainer's monitoring.

## 4. Enforcement Boundaries and Residual Risks

The governance structural checks and required status check configuration have the following boundaries:

- They can detect violations covered by the implemented structural rules.
- The configured required status check has demonstrated actual merge-blocking capability through a controlled negative enforcement test.
- They cannot prove copyright ownership or the legal identity of a copyright holder.
- They cannot replace an independent human review.
- They cannot determine the overall risk classification or approve architectural decisions.
- They cannot establish that every possible repository governance violation is covered by the implemented rules.
- The ruleset reports no declared bypass actors (`bypass_actors: []`) and reports `current_user_can_bypass: never` for the authenticated identity. This establishes the returned configuration and current identity's bypass status, not an exhaustive audit of every possible platform-level authority or exceptional control.
- A required status check does not independently establish that the workflow itself is correct, uncompromised, or comprehensive.

The required status check does not cover the following four residual risk categories:

1. **Decision-record semantics:** The automated gate cannot establish that a decision document accurately represents the underlying facts or that its reasoning is sound.
2. **Risk-classification correctness:** The automated gate cannot independently establish that a decision has been assigned the correct L1, L2, or L3 classification.
3. **Administrative bypass:** The returned ruleset configuration and current identity's `current_user_can_bypass: never` status do not constitute an exhaustive audit of every possible administrative or platform-level authority.
4. **Workflow supply-chain integrity:** The required status check does not prove that the workflow, its actions, runner environment, or all external dependencies are uncompromised.

The previous uncertainty about whether a failing check can actually prohibit merging has been resolved by operational evidence.

The remaining limitations concern semantic, legal, architectural, administrative, operational, and supply-chain boundaries rather than the demonstrated merge-blocking capability.

**Rejected as the permanent solution.**

**Rejected.**

This would combine the original governance requirement with its enforcement implementation, reducing separation of concerns and independent reviewability.

### 5.5 Alternative E — Exempt Documentation Changes

**Rejected.**

Documentation changes can affect governance structure and contracts. A blanket exemption would create an unvalidated change category.

## 10. Reversal and Rollback Procedure

### 10.1 Rollback Principles

The change has two distinct rollback surfaces:

1. Repository code and workflow.
2. GitHub ruleset configuration.

The rollback must preserve the existing original protection rules.

Removing `required_status_checks` without preserving the other three rules is not an acceptable rollback.

The original governance requirement in PR #2 must not be silently deleted or weakened.

Any decision to permanently remove the enforcement requirement must be recorded in a new L2 decision, unless the replacement itself changes a higher-level security boundary or permission model, in which case the highest applicable level governs.

### 10.2 Rollback Ordering

The preferred rollback order is:

1. Record the current repository and ruleset state.
2. Restore the ruleset configuration to the original three-rule configuration.
3. Read the ruleset back and verify that the original protection rules remain active.
4. Restore the workflow and validation implementation to the designated code rollback point.
5. Verify the repository HEAD and workflow state.
6. Archive the rollback evidence.

The configuration rollback precedes the code rollback because the active ruleset must not continue requiring a status check that is being removed from the workflow.

Removing the workflow first could leave the repository in a state where new pull requests cannot obtain the required successful check.

The configuration rollback must be explicitly authorized and recorded. It must not be treated as an incidental side effect of reverting code.
