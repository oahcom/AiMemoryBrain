## 2. Context

### 2.1 原始需求

本次治理落地源于需求：

`REQ-REUSE-2026-11-19-001`

需求的核心原则为：

> 不自己造轮子，除非没有轮子，除非轮子不满足预期。

该需求要求将复用优先原则落实为可审查、可执行、可追溯的工程约束，而不是停留在开发者的个人习惯或非正式约定。

### 2.2 既有治理资产

第三轮认证取证发现，组织既有治理权威仓库：

`oahcom/AiMemoryBrainArchitecture`

已经具备多个与原设计 G-01～G-05 对应的治理机制。

其中包括：

- `00-governance/design-principles.md`：P-01～P-16 已 DECIDED；
- `00-governance/architecture-invariants.md`：I-01～I-24；
- `13-engineering-decisions/technology-research/TECH-REALITY-001-A/`：成熟项目调研证据登记；
- `TECH-REALITY-001-A/research-evidence-register.md`：17 个成熟项目的 Tree SHA、License 和实际检查文件登记；
- `TECH-REALITY-001-A/mature-project-research.md`：成熟项目调查及适用性评价；
- `TECH-REALITY-001-A/independent-review-handoff.md`：独立评审交接机制；
- `reviews/technology-reality/TECH-REALITY-001-A-independent-review.md`：独立评审 `TECH-REALITY-001-A-IR-001`；
- `TECH-REALITY-001-C/agent-integration-decision-record.md`：C-DEC-001～006 决策记录。

其中，`TECH-REALITY-001-A-IR-001` 已有真实执行实例，独立评审发现了 Restate BSL 1.1 许可证遗漏，说明既有独立评审机制并非只有形式文件。

### 2.3 两项真实治理缺口

第三轮认证检索确认以下两项缺失：

**N-01：复用优先原则没有成文。**

组织实践中已经存在建设前调研和成熟项目复用活动，但没有形成明确要求先调查、先登记、优先局部修改、限制独立建设的规范性条款。

**N-06：风险等级与调查深度之间没有梯度。**

既有治理中存在 P1/P2 评审发现分级，以及 Critical/Yes 依赖阻塞分级，但它们分别描述缺陷或发现严重度、依赖阻塞状态，并不规定一次工程变更需要多少调查和复核。

认证检索中，以下关键词及其相关概念均未发现对应的成文治理条款：

- `reuse-first`
- `风险分级`
- `L1 L2 L3`
- `risk level`

因此，N-01 与 N-06 是实际缺口，而不是对已有治理机制的重复计数。

### 2.4 §10.1 判定结果

根据需求包及既有机制比对材料的 §10.1 判定表：

- N-04：已满足；
- 满足数：3；
- 判定阈值：满足数 ≤ 3；
- 最终路线：**B 增强**。

判定依据表明，既有治理资产已经覆盖主线能力，剩余问题集中在两个明确的缺口。

因此，不应机械地将原设计 G-01～G-05 全套重新引入本仓库。

## 3. Decision

**最终决策：采用 B 增强，但仅补齐 N-01 和 N-06 两项真实缺口，其余治理能力通过引用方式复用 `oahcom/AiMemoryBrainArchitecture` 的既有机制。**

不整套引入原设计的 G-01～G-05。

## 4. Alternatives Considered

### Alternative A：B 实施——整套引入 G-01～G-05

**方案**

完整实施原设计中的 G-01～G-05，建立 12 项以上治理制品，形成一套完整的本地治理体系。

**否决理由**

N-04 已满足，既有治理权威仓库已经覆盖大量相关机制。

重新创建完整的 G-01～G-05 会导致：

- 重复建立已有调查登记体系；
- 重复建立成熟度评价机制；
- 重复建立独立评审机制；
- 重复建立决策记录机制；
- 增加跨仓库维护成本；
- 形成两个治理体系之间的同步风险。

更重要的是，整套重建违反本次需求自身的复用优先原则。

在已有机制能够满足需求时，不应为了形式完整而重复建设。

**结论：REJECTED。**

### Alternative B：D 退出——不做任何事，纯引用既有机制

**方案**

不在本仓库增加任何治理文件，仅在工程活动中引用 `AiMemoryBrainArchitecture` 的既有治理机制。

**否决理由**

N-01 和 N-06 是经过检索确认的真实缺口。

检索结果为 0 命中，不是由于统计口径或编号差异造成的计数误差。

具体而言：

- 既有成熟项目调研实践不等于存在强制性的复用优先条款；
- 既有 P1/P2 和 Critical/Yes 分级不等于存在风险等级到调查深度的梯度。

如果完全退出，这两个缺口仍然存在。

本仓库将继续缺乏要求开发者先调查再建设的正式依据，也缺乏与工程变更风险相匹配的调查及复核要求。

**结论：REJECTED。**

### Alternative C：直接在治理权威仓库创建 P-17/P-18

**方案**

将 N-01 和 N-06 直接写入：

`oahcom/AiMemoryBrainArchitecture/00-governance/design-principles.md`

并分别命名为 P-17、P-18。

**否决理由**

本仓库没有该治理权威仓库的写入授权上下文。

治理权威仓库具有独立的治理所有权、评审流程和决策权限。

跨仓库修改治理权威文件，应通过该仓库自己的正式评审与决策流程，而不应由本仓库的工程落地 PR 代劳。

直接创建 P-17/P-18 还会混淆：

- 治理权威仓库的原则编号空间；
- 工程落地仓库的本地条款编号空间；
- 两个仓库各自的决策责任。

因此，本次采用本地 N-01、N-06 条款，并显式声明治理归属。

如果未来确有必要将这两个缺口提升为组织级原则，应另行向治理权威仓库提交增量提案，遵循其正式评审流程。

**结论：REJECTED。**

### Alternative D：B 增强——只补真实缺口

**方案**

只建立 N-01 和 N-06 两份本地条款。

调研证据、成熟度评价、独立评审和决策记录均引用既有机制。

同时完成许可证文件、第三方声明、crate 许可证字段、基线 tag 和 PR 交付。

**接受理由**

该方案：

- 直接解决已认证的两个真实缺口；
- 不重复创建已有治理能力；
- 与组织治理权威保持一致；
- 将范围限制在可验证的八项；
- 保留跨仓库增量治理的后续路径；
- 与需求的复用优先原则一致。

**结论：ACCEPTED。**

## 5. Consequences

### 5.1 正面后果

**治理范围收缩。**

原设计涉及 12 项以上制品。本次决策将治理文件建设范围收缩为两份缺口条款及一份决策记录，避免重复建设。

**降低维护面。**

调研登记、成熟度评价、独立评审和决策记录继续使用治理权威仓库的既有机制，不再建立平行体系。

**提高条款可判定性。**

N-01 的每项规范性要求均包含：

- 要求；
- 判定口径；
- 违例情形。

N-06 则提供：

- 明确的三级风险定义；
- 最低调查深度；
- 决策记录要求；
- 复核要求；
- 升级规则；
- 实际工程场景示例。

由此，条款可以通过实际 PR、决策记录和检查证据进行验证。

**改善许可证透明度。**

根目录 `LICENSE` 与 `THIRD-PARTY-NOTICES` 明确区分项目许可证和第三方数据许可证，避免将 Unicode 数据误认为项目自产内容。

**建立可恢复基线。**

`pre-gov-baseline` 为治理落地前状态提供明确的回滚定位。

### 5.2 负面后果与剩余风险

**双份维护风险。**

本仓库的 N-01、N-06 与治理权威仓库未来可能出现内容重叠或解释差异。

这意味着两个仓库之间存在潜在的双份维护风险。

控制措施：

- 两份条款必须明确声明本地治理归属；
- 不复制既有治理机制的完整内容；
- 使用明确的路径和编号引用既有机制；
- 发生冲突时以治理权威仓库为准；
- 治理权威仓库发生相关变化时，应评估本地引用是否需要更新。

**第三方人工批准能力不足。**

本仓库当前分支保护 ruleset：

- ID：`27711552`
- 名称：`保护分支`
- `enforcement: active`
- 规则：`deletion`、`non_fast_forward`、`pull_request`
- `required_approving_review_count: 0`

由于单人账号的客观约束，当前无法通过要求审批人数大于零的方式建立第三方人工批准闸门。

因此：

- PR 仍必须遵循正式流程；
- 机器检查器必须通过；
- 在可行条件下必须保留非作者复核；
- 高风险变更必须遵循独立评审要求；
- 人类否决权必须保留。

必须明确披露：当前分支保护配置没有第三方批准闸门。本决策依赖机器闸门与非作者复核，其保障强度弱于具有独立人工批准要求的分支保护机制。

不得将机器检查通过描述为等同于第三方人工批准。

不得隐瞒这一限制，也不得声称当前配置已经实现强制第三方审批。

### 5.3 未解决事项

本次决策不意味着组织治理权威仓库的所有治理缺口均已解决。

本次仅针对 N-01 和 N-06 的本地落地作出决定。

其他治理问题应依据各自的认证证据和决策流程单独处理，不得自动扩展本次决策范围。

### 6.2 回滚方式

发生需要撤销本次治理落地的情况时，采用 Git 反向提交方式：

`git revert`

禁止使用：

`git reset --hard`

不得通过重写受保护分支历史的方式回滚本次变更。

### 6.3 回滚步骤

回滚必须遵循以下顺序：

1. 确认需要撤销的提交范围；
2. 核验 `pre-gov-baseline` 指向的精确提交；
3. 创建回滚提交；
4. 通过 Pull Request 提交回滚；
5. 运行相关检查器；
6. 验证代码、构建、测试及许可证文件状态；
7. 留存回滚提交、检查器输出和最终状态证据。

### 6.4 回滚后的要求

回滚不意味着可以删除原始决策记录或审计证据。

必须保留：

- 原始决策记录；
- 原始变更提交；
- 回滚理由；
- 回滚提交；
- 回滚后的检查结果。

如果回滚后仍需要治理条款，应通过新的决策记录重新确定实施范围，不得直接覆盖原决策历史。
