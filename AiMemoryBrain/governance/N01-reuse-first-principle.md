# N-01 复用优先原则（Reuse-First Principle）

- **条款编号**：N-01
- **状态**：**DECIDED**
- **生效范围**：本仓库 `oahcom/AiMemoryBrain`
- **治理归属**：本文件为本仓库的本地落地条款，不构成对 `oahcom/AiMemoryBrainArchitecture` 治理权威的转移或替代；与之冲突时以治理权威仓库为准。
- **上位依据**：
  - `REQ-REUSE-2026-11-19-001`
  - `DEC-RD-2026-11-20-001`

## 1. 条款目的

本条款将复用优先原则转化为本仓库可执行、可审查、可追溯的工程约束。

本仓库在新增能力前，必须优先调查现有实现，判断能否通过复用、集成或局部修改满足需求。独立建设不是默认选择，只有在现有实现确实不可行时才允许采用。

本条款不要求无条件复用，也不以复用数量作为目标。复用决策必须建立在可核验的调查证据、实际适用性分析和明确的决策依据之上。

## 2. 规范性条款

### N-01.1 先查现成再建

**要求**

任何新增能力进入实现阶段之前，必须先检索并登记已有实现。调查范围至少包括：

1. 本仓库已有实现；
2. 同组织仓库已有实现；
3. 公开生态中的成熟实现。

调查证据登记必须至少包含以下字段：

- 候选名称；
- 来源（仓库、项目或发布渠道）；
- 版本或提交钉扎信息；
- 许可证；
- 实际检查的文件清单；
- 调查结论。

版本或提交钉扎必须能够唯一定位被调查的实现。仅登记项目主页、搜索结果或未固定版本的项目名称，不满足钉扎要求。

每个候选项必须有实际检查的文件清单。仅记录项目描述、README 或宣传材料，不得冒充对实现本身的检查。

在调查登记完成之前，不得进入新增能力的实现阶段。

**判定口径**

审查者应能够从决策记录及其关联的调查证据中，核验候选实现、版本或提交、许可证、实际检查文件和调查结论。

至少应能回答：

- 是否检查了本仓库已有实现；
- 是否检查了同组织仓库中的相关实现；
- 是否调查了公开生态中的成熟实现；
- 每个候选项是否具有可核验的版本或提交；
- 是否实际检查了候选实现的相关文件；
- 为什么候选实现适用或不适用。

对于确实不存在候选实现的情况，必须记录搜索范围、检索方式和未发现可用实现的结论，不得以空白登记代替调查。

**违例情形**

以下情况构成违例：

- 未进行调查即开始独立实现；
- 仅凭个人印象宣称没有现成实现；
- 只记录项目名称，没有版本或提交钉扎；
- 只记录许可证名称，没有实际检查证据；
- 没有实际检查文件清单；
- 调查结论没有与具体需求和实现方案关联；
- 在调查登记完成之前进入实现阶段。

### N-01.2 区分独立建设与局部修改

**要求**

当现有实现能够满足需求时，必须优先考虑复用或局部修改既有实现，而不是另起炉灶。

如果现有实现不能完全满足需求，应首先评估能否通过局部修改、适配层、扩展点或组合方式满足需求。

选择独立建设时，必须书面说明为什么局部修改不可行。说明必须是技术、架构、许可、安全、维护或其他可核验约束层面的不可行性，不得以主观便利作为理由。

**判定口径**

审查者应能够从决策记录中确认：

1. 已识别至少一个最相关的现有实现，或者已证明不存在相关实现；
2. 已评估复用和局部修改的可行性；
3. 如选择独立建设，已明确指出阻止局部修改的具体约束；
4. 该约束具有可验证的证据，而不是未经论证的偏好；
5. 独立建设方案的收益和维护成本已纳入比较。

“不可行”必须表示在当前约束下无法达到需求，而不是实现成本较高、开发者不熟悉、代码风格不同或短期内不方便。

**违例情形**

以下情况构成违例：

- 已有实现可满足需求，却无理由重新建设；
- 未评估局部修改就选择独立建设；
- 仅以“不方便”“不熟悉”“不喜欢现有设计”作为理由；
- 将局部修改的成本较高直接等同于不可行；
- 声称不可行但没有说明具体约束及证据；
- 通过改写需求描述来掩盖可复用实现的存在。

### N-01.3 保留调查与豁免依据

**要求**

调查结论、复用决策、独立建设理由及任何豁免依据，必须与相应决策记录同址归档，并绑定精确提交。

归档内容必须能够在仓库中长期访问和复核，不得仅保存在会话、聊天记录、临时文件或个人笔记中。

提交钉扎应能够唯一定位相关调查材料和决策记录对应的代码状态。

**判定口径**

审查者应能够从仓库历史中定位：

- 对应需求；
- 调查证据登记；
- 复用或独立建设决策；
- 豁免理由（如存在）；
- 关联的精确提交。

同址归档可以通过同一决策目录及其明确引用的证据文件实现，但不得依赖无法持久访问的外部会话内容。

**违例情形**

以下情况构成违例：

- 调查结论仅存在于聊天记录；
- 豁免理由仅由执行者口头说明；
- 决策记录没有绑定精确提交；
- 证据文件与决策记录之间没有可核验的关联；
- 变更完成后无法恢复当时的调查依据；
- 以会话链接代替仓库内的正式决策记录。

### N-01.4 禁止拆分规避

**要求**

不得将一个完整的自建能力需求拆分成多个较小需求、提交或 PR，以规避复用审查。

复用审查的对象是能力边界，而不是提交粒度、PR 数量或代码文件数量。

当多个子任务共同实现一个完整能力时，必须在能力层面进行统一复用调查和决策。

**判定口径**

审查者应根据以下因素识别能力边界：

- 相同或连续的业务目标；
- 共同的输入、输出或对外契约；
- 共同的数据来源；
- 共同的核心算法或执行路径；
- 相互依赖的实现步骤；
- 合并后构成同一完整功能的多个改动。

如果多个变更在功能上共同构成一个能力，则应统一进行复用审查，即使它们分布在不同提交、PR、目录或开发阶段。

**违例情形**

以下情况构成违例：

- 将一个完整能力拆成多个小 PR，以使每个 PR 看起来不需要复用调查；
- 先提交底层实现，再以独立需求名义补充其余能力以绕开审查；
- 将同一能力的算法、数据、接口和构建支持拆开后分别宣称为无关需求；
- 以提交数量或文件数量作为无需统一审查的依据。

## 3. 既有机制的复用引用

本节采用**引用而非重建**的方式使用 `oahcom/AiMemoryBrainArchitecture` 已有治理机制。

本仓库不重新创建一套平行的调研、成熟度评估、独立评审和决策记录框架。

### 3.1 调研证据登记体例

引用：

`AiMemoryBrainArchitecture/13-engineering-decisions/technology-research/TECH-REALITY-001-A/research-evidence-register.md`

该登记文件已提供成熟项目调查的证据登记体例，包括：

- 项目及来源；
- Tree SHA；
- License；
- 实际检查的文件清单。

本仓库执行 N-01.1 时，应复用这一登记体例，不得自行削弱其版本钉扎和证据要求。

### 3.2 成熟度评价体例

引用：

`AiMemoryBrainArchitecture/13-engineering-decisions/technology-research/TECH-REALITY-001-A/mature-project-research.md`

复用其三段式评价结构：

1. `Observed implementation`
2. `Applicable lessons`
3. `Do not copy`

三段式分别用于记录实际观察到的实现、对本项目适用的经验以及明确不应复制的部分。

不得将项目成熟度简单等同于项目知名度、GitHub Star 数量或文档完整程度。

### 3.3 独立评审机制

引用：

`AiMemoryBrainArchitecture/13-engineering-decisions/technology-research/TECH-REALITY-001-A/independent-review-handoff.md`

复用其中：

`A DIFFERENT SESSION — NOT THE AUTHOR`

这一独立性要求。

独立评审必须由不同于作者的评审主体执行，不能将作者自己的复查重新命名为独立评审。

引用已实际执行的独立评审实例：

`TECH-REALITY-001-A-IR-001`

该实例的结论为 `REVISE`，并实际发现 Restate BSL 1.1 许可证遗漏，证明独立评审具有发现作者遗漏的实际价值。

本仓库引用该机制及实例，不重新定义一套独立评审流程。

### 3.4 决策记录体例

引用：

`AiMemoryBrainArchitecture/13-engineering-decisions/technology-research/TECH-REALITY-001-C/agent-integration-decision-record.md`

复用 C-DEC 决策记录体例中的四项核心要素：

- `Status`
- `Alternatives`
- `Consequences`
- `Reversal`

决策记录必须展示最终状态、被考虑的替代方案及其取舍、决策后果和回滚方式。

不得以仅记录最终结论的简短说明替代可追溯的工程决策记录。
