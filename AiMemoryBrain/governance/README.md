# 治理规则与决策记录目录

## 1. 目录用途

`governance/` 用于保存本仓库适用的治理规则、执行约束及正式决策记录。

本目录的目的在于将组织治理要求映射到本仓库的实际开发和维护活动。

治理文件必须具有明确的来源、适用范围和执行责任。

本目录不替代组织级治理权威仓库。

## 2. 目录结构

当前治理目录采用以下结构：

```text
governance/
├── README.md
├── N01-reuse-first-principle.md
├── N06-risk-tiered-decision-depth.md
├── decisions/
│   ├── DEC-RD-YYYY-MM-DD-NNN.md
│   └── DEC-RD-YYYY-MM-DD-NNN-amendment-NN.md
└── evidence/
    ├── ruleset-27711552-v58744075-before.json
    └── ruleset-27711552-v58800168-after.json
```

各部分职责如下。

### 2.1 N01：Reuse First Principle

文件：

`N01-reuse-first-principle.md`

定义本仓库在新增治理机制、架构机制及工程能力之前，优先调查和评估既有内部资产与公开生态方案的原则。

重点包括：

- 既有内部资产识别。
- 公开生态候选方案调查。
- 来源与版本钉扎。
- 许可证识别。
- 实际文件范围检查。
- 适用性评价。
- 复用或不复用结论。

公开生态调查不能仅登记项目名称。

完整调查必须具备 N-01.1 所要求的证据字段。

### 2.2 N06：Risk-Tiered Decision Depth

文件：

`N06-risk-tiered-decision-depth.md`

定义本仓库根据变更风险等级决定调查深度、决策记录要求和复核要求的原则。

适用范围包括：

- 普通工程变更。
- 重大架构变化。
- 许可证变更。
- 权利授予。
- 第三方版权内容。
- 其他满足高风险条件的变更。

风险等级必须在决策记录中明确声明。

不得仅凭变更规模、代码行数或文件数量推断风险等级。

尤其对于 L3 变更，应执行相应深度的调查和独立复核。

独立评审必须在适用要求规定的时点完成。

### 2.3 decisions/

`decisions/` 保存本仓库正式治理决策。

每份决策记录应包含：

- 决策编号。
- 决策日期。
- 变更范围。
- 风险等级。
- 决策依据。
- 调查证据。
- 副作用评估。
- 剩余风险。
- 回滚方案。
- 执行责任。
- 审批及复核状态。

原始决策记录的事后补正件与对应原始记录保存在同一目录中，文件名使用原决策编号并追加 `-amendment-NN` 标识。

查阅原始决策记录时，应同时检查 `decisions/` 目录中是否存在以该决策编号为前缀的补正件。补正件用于记录事后补正，不修改、不覆盖、不替换原始决策记录。

决策记录是治理过程的正式证据，不应仅作为项目说明文档使用。

### 2.4 evidence/

`evidence/` 用于存放治理决策与执行变更的支撑证据。

该目录当前包含两份 ruleset 配置快照：

- `ruleset-27711552-v58744075-before.json`
- `ruleset-27711552-v58800168-after.json`

这两份文件分别保留相关 ruleset 变更前后的配置记录，
作为治理决策的支撑证据。它们不能替代对应的决策记录
或评审报告。

## 3. 本地治理条款与组织级治理权威的关系

本仓库的治理文件属于本地适用规则。

组织级治理权威仓库为：

`oahcom/AiMemoryBrainArchitecture`

地址：

https://github.com/oahcom/AiMemoryBrainArchitecture

本地治理文件用于将组织治理原则应用于当前仓库。

组织级治理权威仓库用于保存更高层次的治理原则、架构不变量及正式治理要求。

两者之间的关系为：

1. 本地文件可以细化组织级要求。
2. 本地文件可以增加适合本仓库的执行步骤。
3. 本地文件不得擅自降低组织级强制要求。
4. 本地文件不得与组织级权威要求形成实质冲突。
5. 如果存在冲突，以组织级治理权威为准。
6. 冲突应通过正式决策和必要的本地修订解决。

本地治理文件不得通过自行解释改变组织级规则的含义。

## 4. 编号空间约定

本仓库使用：

`N-xx`

作为本地治理规则编号空间。

例如：

- N-01：Reuse First Principle。
- N-06：Risk-Tiered Decision Depth。

本仓库不占用组织级原则编号空间：

`P-xx`

`P-xx` 属于组织级治理原则编号空间。

本仓库引用组织级原则时，应保留原始编号及其来源，不得将其重新编号为本地原则。

同样，组织级架构不变量使用的：

`I-xx`

也不属于本仓库本地治理规则编号空间。

本地规则与组织级原则、架构不变量应保持可追溯关系。

## 5. 决策记录命名规则

正式决策记录采用：

`DEC-RD-YYYY-MM-DD-NNN.md`

补正件采用：

`DEC-RD-YYYY-MM-DD-NNN-amendment-NN.md`

字段说明：

| 字段 | 含义 |
|---|---|
| DEC-RD | 治理决策记录前缀 |
| YYYY-MM-DD | 决策日期 |
| NNN | 决策序号 |
| amendment | 事后补正文件标识 |
| NN | 补正件序号 |

命名格式示意（非实际文件清单）：

```text
DEC-RD-YYYY-MM-DD-NNN.md
DEC-RD-YYYY-MM-DD-NNN-amendment-NN.md
```

以上仅用于说明原始决策记录与补正件的命名格式，不代表目录中的实际文件清单。具体文件以 `decisions/` 目录中的实际内容为准。

要求：

- 原决策记录使用稳定编号。
- 补正件与原决策记录保持相同主体编号。
- 补正件序号递增。
- 不得将补正件伪装成新的原始决策记录。
- 不得覆盖原决策记录以隐藏历史缺陷。

## 6. 补正件与原始记录的关系

**补正件不得修改原文件正文。**

补正件用于：

1. 补充原决策记录未覆盖的事实。
2. 明确原记录未声明的风险等级。
3. 增加事后获得的调查证据。
4. 记录未解决事项。
5. 明确整改责任。
6. 保存历史程序缺陷。
7. 建立后续执行约束。

补正件必须引用原决策记录的准确路径和编号。

补正件不得：

- 追溯性修改原始决策结论。
- 伪造原始审批时间。
- 将事后评审写成合并前评审。
- 将未完成的调查写成已完成。
- 将尚未确认的版权归属写成已确认。
- 删除原记录中的历史事实。

如果原决策记录存在实质错误，应另行建立补正件，说明原内容、错误原因、正确事实和证据。

原文件仍应保留。

## 7. 风险等级与决策记录

每份正式决策记录必须明确风险等级。

风险判断应依据：

`N06-risk-tiered-decision-depth.md`

不得只填写变更规模而省略风险判断。

对于 L3 变更，应明确：

- L3 命中条件。
- 调查深度。
- 依赖影响。
- 维护影响。
- 许可影响。
- 运维影响。
- 回滚方案。
- 未闭合事项。
- 独立评审要求。
- 责任人及最终审批状态。

风险等级与实际评审程序必须保持一致。

不能仅通过在文档中增加 L3 标签证明 L3 要求已经执行。

## 8. 公开生态复用调查

依据 N-01，新增机制之前必须调查既有内部资产和公开生态。

公开生态调查至少应记录：

1. 候选名称及来源。
2. 版本或 Tree SHA。
3. 许可证。
4. 实际检查文件清单。
5. 适用性评价。
6. 最终复用或不复用结论。

仅记录项目名称不构成完整调查。

没有完成调查时，应明确标注：

`NOT_COMPLETED`

不得把候选范围记录描述为已经完成的评估。

## 9. 许可证与第三方内容

涉及许可证或权利授予的治理变更，应明确记录：

- 项目许可证。
- 版权持有者。
- 授权依据。
- 直接依赖。
- 传递依赖。
- 第三方数据。
- 第三方许可。
- THIRD-PARTY-NOTICES 覆盖。
- 实际分发场景。
- 尚未解决的法律和许可风险。

`Cargo.lock` 是 Cargo 实际解析依赖版本的权威记录。

依赖清单必须与实际锁定版本对应。

没有证据时，不得推定版权持有者、授权资格或传递依赖覆盖状态。

## 10. 运维影响评估

治理决策应当覆盖依赖、维护、许可和运维四个维度。

对于本地构建工具，运维评估应当围绕实际影响展开。

例如：

- 构建期行为。
- 本地运行。
- 数据锁校验。
- 文件完整性。
- 依赖更新。
- 发布及分发条件。
- 服务端运行是否存在。

如果项目没有服务端运行职责，应明确说明不适用的内容及其理由。

不能因为项目不是在线服务就完全省略运维维度。

## 11. 评审与合并时序

适用治理规则要求合并前独立评审的变更，必须在合并前完成独立评审并取得相应结论。

评审对象必须绑定精确版本。

已经合并的变更如果事后发现缺少评审，应：

1. 如实登记历史缺陷。
2. 形成事后独立评审报告。
3. 形成必要的补正件。
4. 明确尚未闭合事项。
5. 为后续变更建立合并前门禁。

**事后评审不能追溯性地治愈历史时序缺陷。**

补正件不得改变原决策记录的历史正文。

## 12. 文件维护及历史保护

治理文件应保持稳定、可追溯和可审计。

任何实质修改都应通过正式变更记录完成。

修改已有规则时，应保留：

- 原文件版本。
- 修改原因。
- 修改依据。
- 适用范围。
- 影响分析。
- 审核结论。

修改已有决策时，应采用独立补正件。

修改已有独立评审结论时，应建立新的补充评审记录。

本目录的目标不仅是保存治理规则，还要保证治理规则自身能够被执行、验证和审计。
