# N-06 风险分级的决策与调查深度（Risk-Tiered Decision Depth）

- **条款编号**：N-06
- **状态**：**DECIDED**
- **生效范围**：本仓库 `oahcom/AiMemoryBrain`
- **治理归属**：本文件为本仓库的本地落地条款，不构成对 `oahcom/AiMemoryBrainArchitecture` 治理权威的转移或替代；与之冲突时以治理权威仓库为准。
- **上位依据**：
  - `REQ-REUSE-2026-11-19-001`
  - `DEC-RD-2026-11-20-001`

## 1. 为什么需要梯度

调查深度一刀切会造成两种相反的问题：低风险改动被过度审查，增加不必要的工程成本；高风险改动被同等轻量地放过，无法获得与其风险相匹配的调查、评审和回滚保障。

本条款通过 L1、L2、L3 三级梯度，将调查成本、决策记录要求和复核强度匹配到变更的实际风险。

本条款回答的是：

**这次变更需要多少调查、多少决策记录和多少复核？**

它不替代缺陷严重度、评审发现等级或依赖阻塞等级。

## 2. 三级风险定义

### 2.1 风险等级与最低要求

| 等级 | 判定条件 | 最低调查深度 | 决策记录要求 | 复核要求 |
|---|---|---|---|---|
| **L1 低风险** | 不改变对外契约；不引入新依赖；不触及许可证与数据来源；能够被现有测试完全覆盖 | 变更说明 + 现有测试通过证据 | PR 描述即可 | 机器闸门，检查器全绿 |
| **L2 中风险** | 引入新依赖；修改公开 API 或契约；修改构建脚本；变更数据格式 | 依赖、许可证和维护状态核查 + 影响面分析 + 新增或更新的测试 | 决策记录文件，`Status`、`Alternatives`、`Consequences`、`Reversal` 四要素齐全 | 机器闸门 + 非作者复核 |
| **L3 高风险** | 引入新数据来源或第三方版权内容；变更安全边界或权限模型；变更持久化格式且无向后兼容；涉及许可证变更或权利让渡；跨 Owner 契约变更 | L2 全部要求 + 独立评审（`NOT THE AUTHOR`）+ 回滚方案 + 副作用评估（依赖、维护、许可、运维四个维度） | 决策记录 + 独立评审报告 + 回滚点（tag 或精确提交） | 独立评审通过 + 人类否决权窗口 |

### 2.2 L1 低风险

**判定条件**

变更同时满足以下全部条件：

- 不改变对外契约；
- 不引入新依赖；
- 不触及许可；
- 不改变数据来源；
- 不改变持久化格式；
- 不改变安全边界或权限模型；
- 现有测试能够完整覆盖变更行为。

**最低调查深度**

必须提供：

1. 简明变更说明；
2. 相关现有测试通过证据；
3. 检查器执行结果。

**决策记录要求**

可以直接在 PR 描述中记录变更说明、影响范围和测试证据，不强制要求单独创建决策记录文件。

**复核要求**

通过机器闸门即可。相关检查器必须全部通过，不得存在未解释的失败。

### 2.3 L2 中风险

**判定条件**

变更命中以下任意一项，且未命中 L3 条件：

- 引入新依赖；
- 修改公开 API 或契约；
- 修改构建脚本；
- 变更数据格式。

**最低调查深度**

必须完成：

1. 依赖核查（适用时）；
2. 许可证核查（适用时）；
3. 维护状态核查；
4. 影响面分析；
5. 新增或更新的测试；
6. 机器检查器执行。

依赖核查至少应覆盖依赖来源、版本钉扎、许可证和维护状态。

影响面分析必须说明受影响的模块、调用方、构建流程及兼容性。

**决策记录要求**

必须在仓库中创建独立决策记录文件，完整包含：

- `Status`
- `Alternatives`
- `Consequences`
- `Reversal`

四项均不得缺失。

**复核要求**

必须同时满足：

- 机器闸门通过；
- 非作者复核完成。

作者自我检查不能替代非作者复核。

### 2.4 L3 高风险

**判定条件**

变更命中以下任意一项：

- 引入新的数据来源；
- 引入第三方版权内容；
- 变更安全边界；
- 变更权限模型；
- 变更持久化格式且不提供向后兼容；
- 涉及许可证变更；
- 涉及权利让渡；
- 涉及跨 Owner 契约变更。

**最低调查深度**

必须满足 L2 的全部要求，并额外完成：

1. 独立评审；
2. 回滚方案；
3. 副作用评估。

独立评审必须遵守：

`A DIFFERENT SESSION — NOT THE AUTHOR`

独立评审主体不得是变更作者。独立评审应针对精确提交进行，并形成可归档的评审报告。

副作用评估必须覆盖四个维度：

| 维度 | 最低评估内容 |
|---|---|
| 依赖 | 新增、删除、升级依赖及其传递影响 |
| 维护 | 长期维护成本、上游维护状态、版本演进风险 |
| 许可 | 许可证兼容性、版权归属、再分发义务及权利变化 |
| 运维 | 部署、构建、运行、恢复、监控和故障处理影响 |

回滚方案必须明确：

- 回滚目标；
- 回滚操作；
- 回滚后检查；
- 数据或状态恢复要求；
- 回滚操作的证据保留方式。

**决策记录要求**

必须同时具备：

1. 完整决策记录；
2. 独立评审报告；
3. 可验证回滚点。

回滚点必须是明确的 tag 或精确提交，不得仅使用可变分支名称。

**复核要求**

必须满足：

- 机器闸门通过；
- 独立评审通过；
- 人类否决权窗口已保留。

人类否决权不得因自动化检查通过而被取消。

## 3. 风险等级升级规则

### 3.1 不确定性升级

当无法确定变更属于哪个风险等级时，必须按较高一级处理。

不得在证据不足时默认选择较低等级。

### 3.2 多条件命中

同一变更同时命中多个等级的判定条件时，取其中最高等级。

例如，一个新增依赖的变更同时引入新的第三方版权数据，则整体按 L3 处理，而不是将依赖部分按 L2、数据部分按 L3 后分别降低整体复核要求。

### 3.3 初判与确认

风险等级由变更提出者初判，由复核者确认。

变更提出者必须在 PR 描述或决策记录中声明初判等级及其依据。

复核者应检查是否遗漏更高等级的触发条件。

不得由同一人在没有复核的情况下自行降低风险等级。

### 3.4 风险等级绑定

风险等级应绑定具体变更范围和精确提交。

当变更范围扩大、依赖增加、数据来源变化或契约发生变化时，必须重新评估风险等级。

原有风险等级不得自动沿用到实质不同的变更。

## 4. 与既有分级机制的衔接

本节采用**引用而非重建**的方式使用 `oahcom/AiMemoryBrainArchitecture` 中已经存在的分级机制。

本条款不修改既有分级定义，也不将其合并为一个统一等级。

### 4.1 缺陷严重度 S0/S1/S2

缺陷严重度 `S0/S1/S2` 是缺陷分级，回答：

**问题有多严重？**

它决定缺陷处置的严重程度，不直接决定某次工程变更需要多少调查深度。

### 4.2 评审发现 P1/P2

评审发现 `P1/P2` 是评审发现分级，回答：

**发现的问题有多严重？**

它用于记录评审过程中发现的问题及其处理优先级，不替代变更风险等级。

### 4.3 依赖阻塞 Critical/Yes

引用：

`AiMemoryBrainArchitecture` 中的 `owner-dependency-register.md`。

其中 `Critical/Yes` 属于依赖阻塞分级，回答：

**该依赖是否构成关键阻塞？**

它用于标识依赖关系及其阻塞属性，不回答本次变更需要进行多少调查。

### 4.4 三个维度分别适用

三个维度相互独立：

| 分级机制 | 回答的问题 | 管理对象 |
|---|---|---|
| N-06：L1/L2/L3 | 这次变更需要多少调查与复核？ | 变更风险及调查深度 |
| S0/S1/S2、P1/P2 | 问题或发现有多严重？ | 缺陷及评审发现 |
| Critical/Yes | 依赖是否构成关键阻塞？ | 依赖关系及阻塞 |

三者可以叠加，不得互相替代。

例如：

- 一个 L1 变更在实施过程中触发 S0 缺陷时，缺陷处置仍必须按照 S0 要求执行，不能因为变更最初被判定为 L1 而降低缺陷处置要求。
- 一个 L3 变更的独立评审发现问题时，该问题仍须按照 P1/P2 进行发现分级记录，不能以 L3 代替发现等级。
- 一个 L2 变更依赖某项 Critical/Yes 依赖时，依赖阻塞属性仍须独立登记，不能以 L2 代替依赖阻塞分级。

## 5. 判定示例

以下示例以本仓库实际文件、配置和数据结构为对象。

| 变更示例 | 风险等级 | 判定理由 | 最低证据要求 |
|---|---|---|---|
| 修改 `src/normalization.rs` 的注释与内部变量名，不改变行为、契约和测试覆盖范围 | **L1** | 不改变对外契约、不引入依赖、不改变许可或数据来源 | 变更说明 + 现有测试通过证据 |
| `Cargo.toml` 新增一个 crate 依赖 | **L2** | 引入新依赖，需要核查版本、许可证、维护状态和影响面 | 依赖及许可调查 + 决策记录 + 测试 + 非作者复核 |
| 升级 `ucd/15.1.0/` 到 `ucd/16.0.0/` | **L3** | 引入新的 Unicode 数据版本及第三方版权内容，改变数据来源和验证基线 | L2 全部要求 + 独立评审 + 数据迁移及回滚方案 + 四维副作用评估 |
| 将 `Cargo.toml` 的 `license = "UNLICENSED"` 改为 `license = "Apache-2.0"` | **L3** | 涉及许可证变更和权利让渡，可能改变项目及分发物的许可状态 | 完整许可依据 + 决策记录 + 独立评审 + 精确回滚点 |
| 收紧 `build.rs` 的校验逻辑 | **L2** | 修改构建脚本，可能改变构建时接受或拒绝的输入及构建结果 | 影响面分析 + 测试更新 + 决策记录 + 非作者复核 |
| 修改 `ucd/15.1.0/derived/normalization-index.json` 的字段结构 | **L2** | 变更数据格式，可能影响构建逻辑、读取方及数据兼容性 | 格式变更说明 + 影响面分析 + 测试 + 决策记录 |

### 5.1 示例的适用边界

上述等级以示例明确描述的变更范围为基础。

如果实际变更同时涉及更高等级条件，必须按最高等级重新判定。

例如：

- 修改 `src/normalization.rs` 不仅涉及内部变量名，还改变对外规范化契约时，应升级为 L2。
- 修改 `build.rs` 同时引入新的第三方数据来源时，应升级为 L3。
- 修改派生索引格式同时造成不可向后兼容的持久化格式变更时，应根据实际持久化边界重新评估，命中 L3 条件时按 L3 处理。

## 6. 豁免与降级

任何豁免或风险等级降级必须有书面依据，并与对应决策记录同址归档。

书面说明至少包括：

1. 原始风险等级；
2. 请求豁免或降级的具体要求；
3. 豁免或降级理由；
4. 支持该理由的可核验证据；
5. 剩余风险；
6. 补偿性控制；
7. 决策责任主体；
8. 对应精确提交。

不得以“时间紧”“人手不足”“实现简单”或“改动很小”作为唯一降级理由。

豁免不得自动扩展到其他变更，也不得作为后续同类变更的默认先例。

涉及 L3 的独立评审要求时，不得通过作者自我声明或机器检查结果将独立评审替换为自审。

## 7. 生效与修订

本条款自合并进入本仓库 `main` 分支后生效。

任何修订必须：

1. 通过 Pull Request 提交；
2. 引用相应决策记录；
3. 明确列出修改内容；
4. 留存修订理由；
5. 说明对现有风险判定及复核流程的影响；
6. 保持与 `oahcom/AiMemoryBrainArchitecture` 治理权威的归属关系声明。

修订不得通过模糊判定条件、删除高风险触发条件或降低独立评审要求的方式规避本条款。
